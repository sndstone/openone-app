# OpenOne desktop app

A Windows and macOS app for running and testing the OpenOne decision model locally (or against a remote GPU server).
It has:
- onboarding: hardware check, runtime install, model import with SHA256SUMS verification, a test decision;
- easy mode: a tool-call gate and a bucket classifier;
- advanced mode: a JSON editor with live validation, raw mode, batch JSONL scoring, temperature/threshold/policy tuning;
- logs and a feedback export.

Feasibility findings and measurements are in [FEASIBILITY.md](FEASIBILITY.md).

## Getting the app and the model
- **App:** the installers are on the [v0.1.0 release](https://github.com/sndstone/openone-app/releases/tag/v0.1.0)
  (Windows; unsigned). macOS builds come from the CI workflow.
- **Model:** the packages are on the [model-v9-r16 release](https://github.com/sndstone/openone-app/releases/tag/model-v9-r16).
  GitHub limits release files to 2 GiB, so each zip is split into parts. Join the parts, check the hash, then import the
  zip in the app:

  ```bash
  # macOS / Linux
  cat openone-decider-v9-r16-bf16.zip.0* > openone-decider-v9-r16-bf16.zip
  shasum -a 256 openone-decider-v9-r16-bf16.zip
  ```
  ```bat
  :: Windows (cmd)
  copy /b openone-decider-v9-r16-bf16.zip.001+openone-decider-v9-r16-bf16.zip.002 openone-decider-v9-r16-bf16.zip
  certutil -hashfile openone-decider-v9-r16-bf16.zip SHA256
  ```

  | Package | Use | zip sha256 |
  | --- | --- | --- |
  | `openone-decider-v9-r16-bf16.zip` (3.8 GB) | the reference model; any local device, or vLLM | `03db485da12078c1eabb2506e65ea5d5ef36c1900b8db4ae483a0b38076a18e3` |
  | `openone-decider-v9-r16-fp8.zip` (2.7 GB) | vLLM on Ada/Hopper/Blackwell; elsewhere it runs as the bf16 fallback | `e4b4359fa12f10a622aab96ea5385f389a4d10504e8c99febe7d168f49c97e2b` |

  The app also checks every file inside the zip against the package's own `SHA256SUMS` when it imports it.
- **Model license:** the weights are [`Mapika/decider-2b`](https://huggingface.co/Mapika/decider-2b) (Apache-2.0)
  with a merged rank-16 LoRA (OpenOne use-case fine-tune), distributed under Apache-2.0. Training data: synthetic rows
  plus public datasets. The `README-BACKUP.md` inside each package predates this release and still calls it a private
  backup.

## What the model does, and what the app does
OpenOne is not a chat model. One decision works like this:
1. The app builds the trained Decider prompt for `{state, question}`.
2. One forward pass reads the logits of the option letters at the final `" ("` token.
3. The app applies `softmax(logits / T)` with the use-case temperature from the package's `openone.json`.
4. Then it applies the thresholds (also from `openone.json`).

**The answer JSON is built by the app, not generated by the model.** So "syntax" here means two things:
- **Requests** are parsed strictly (no duplicate keys, no NaN/Infinity), then checked against the request JSON Schema
  plus semantic rules. Errors carry JSON paths and line/column numbers.
- **Every response** the app produces is checked against the response JSON Schema plus consistency rules:
  - the probabilities sum to 1;
  - the choice is the argmax;
  - the verdict follows from the thresholds;
  - the temperatures equal the settings;
  - usage adds up;
  - the response survives a strict JSON round trip.

A response that fails any check is written to `feedback.jsonl`. **Logs & feedback → Export feedback** zips it for
sending back. Users can also report a case by hand (the "Report" button on any result).

Invalid *requests* are the user's own input, so they are not logged as feedback. They are shown in the UI with JSON
paths and line numbers instead, and nothing is scored. The feedback log stays reserved for model and response failures.

## Stack, and why
| Part | Choice | Why |
| --- | --- | --- |
| Window | **pywebview** (WebView2 on Windows, WKWebView on macOS) | Uses the OS web view: a few MB instead of the ~150 MB of an Electron shell. No Node or Rust toolchain. One language (Python) end to end. |
| UI | Vanilla HTML/CSS/JS, no build step | Nothing to compile. All model/user text goes in as text nodes (no `innerHTML`). |
| App process | Python 3.12, stdlib HTTP server on 127.0.0.1 with a session token and a Host check | The model runtime is Python (torch + transformers + the Decider prompt code). Keeping the app in Python shares one implementation of prompt building, validation and response building with the worker and the server. |
| Inference | **Separate runtime process** (standalone Python + torch), JSON lines over stdio | Keeps torch (0.5–4 GB depending on accelerator) out of the installer. Lets onboarding install the build that matches the hardware (CPU / CUDA / Intel XPU / Apple MPS). Keeps the UI responsive. |
| Packaging | PyInstaller (one-folder), Inno Setup (Windows installer), `hdiutil` (macOS dmg) | Mature tools for both OSes. The app bundle is ~25 MB, and the installer ~12 MB. |
| Remote | FastAPI + vLLM 0.31 container (`server/`) | FP8 only runs in vLLM on Linux + NVIDIA Ada/Hopper/Blackwell. |

Tauri was considered: it is smaller still, but it would add a Rust toolchain and a second language, and we would still need
the Python sidecar for inference. Electron was considered and dropped: it adds a large runtime and Node tooling for no gain here.

**The model package is never bundled.** It is imported at onboarding from the zip (or an extracted folder). Every file
is hashed while it is copied into the app data folder, and any mismatch aborts the import. The app never executes code
from an imported package: it uses its own verified copy of the Decider prompt code (`core/openone_core/vendor`) and
warns if a package ships a different one.

## Backends
- **Local:** the bf16 package on CUDA, Intel XPU, Apple MPS or CPU. Runtimes are installed by onboarding into the data
  folder:
  - python-build-standalone 3.12.15 (sha256-pinned);
  - torch 2.14.1 and transformers 5.20.2 (pinned).
  - You can also point the app at your own Python that already has torch and transformers.
- **FP8 on hardware without FP8** (anything local): the FP8 package is dequantized to bf16 at load, and the UI shows
  the fallback warning.
  - The dequantization is byte-identical to the cluster reference `quant/dequant_fp8.py` (dequantized weights sha256
    `a14fc531…`).
  - You choose whether to cache the 3.8 GB result or redo the dequantization on every load (about 6–9 s).
  - The fallback uses its **own fitted numbers**, fitted 2026-10-20 under vLLM bf16: T bucket 1.34, T tool call 1.28,
    auto-run 0.80, alarm 0.4133.
  - They are kept in `core/openone_core/fallback_settings.json` and written into the cached copy's `openone.json` as
    `runtime: "bf16 (dequantized from FP8)"`.
  - The UI labels them "fitted under vLLM". On the local PyTorch backend a note says the difference is noise-level.
  - Quality vs the real bf16 model on real traffic: mean |Δp| 0.0065–0.0078 (true FP8 0.011–0.015), about half of FP8's
    argmax flips, false alarms 108 / 114 / 120 (bf16 / fallback / FP8), block leaks 10 / 11 / 9 of 1,089.
  - An FP8 package the app has no fitted numbers for falls back to the bf16 package's numbers, marked **provisional**.
- **Remote:** the gate service from `server/` (vLLM, native FP8). The app reads the server's `/health`: model, mode, the
  numbers it applies and their source. The app then builds and validates the responses itself, from `/v1/score`
  letter log-probs. `/v1/systemone` gives agent harnesses the full validated response directly.

### Running the gate service (Linux + NVIDIA + Docker)
```bash
# on the GPU box, from a copy of this folder; the package folder is an extracted + verified OpenOne package
server/run_gate.sh ~/openone-gate/models/openone-decider-v9-r16-fp8 0 8130     # GPU index 0, port 8130
```
- The API key is created in `~/openone-gate/gate.key` (mode 600) and never printed. Copy it into the app's Settings,
  under Remote.
- An FP8 package on a GPU without FP8 (compute capability < 8.9) is dequantized to bf16 automatically, and `/health`
  says so.
- For a bf16 package served by vLLM, the bundle README gives vLLM-fitted numbers. Pass them with
  `OPENONE_SETTINGS_FILE=/path/openone-vllm.json`.

On Windows with an NVIDIA Ada+ GPU, the same image runs under Docker Desktop (WSL2): `run_gate.sh` from a WSL shell.
The app then uses `http://127.0.0.1:8130`. Not tested here (this PC has no NVIDIA GPU).

## Building
| Target | Command | Output (in `release/`) |
| --- | --- | --- |
| Windows | `powershell -ExecutionPolicy Bypass -File packaging\windows\build.ps1 [-Offline]` | `OpenOne-Setup-0.1.0-win-x64.exe` (per-user Inno Setup installer), `OpenOne-0.1.0-win-x64-portable.zip`, `-offline` variants with the CPU runtime bundled, `SHA256SUMS.txt` |
| macOS (Apple Silicon) | `packaging/macos/build.sh [--offline]` on a Mac with Python 3.12 | `OpenOne-0.1.0-macos-arm64.dmg`, `.app.zip` |
| Both, in CI | `.github/workflows/build.yml` (manual dispatch) | workflow artifacts (kept 14 days) |

Details:
- **Windows.** The build needs Python 3.12 and Inno Setup 6. `build.ps1` finds `ISCC.exe` in `_tools\innosetup`,
  Program Files or LocalAppData.
- **macOS.** No Mac was available, so these scripts have not been run. Builds are ad-hoc signed unless you set
  `MACOS_SIGN_IDENTITY` (and `NOTARY_PROFILE` for notarization).
  - Unsigned: right-click → Open on first launch, or run `xattr -dr com.apple.quarantine /Applications/OpenOne.app`.
  - Intel Macs: the app builds, but PyTorch no longer ships Intel-Mac wheels, so it runs with the remote backend only.
- **Signing.** The Windows installer is unsigned. To sign it, run `signtool` on the exe with your certificate.
- **CI.** The workflow runs:
  - the core unit tests;
  - both builds;
  - an inference smoke test with a tiny random Qwen3.5 model and the public base-model tokenizer, so CI never
    downloads the 3.8 GB weights. On the macOS runner it uses MPS if the runner exposes it.
- **Publishing.** Installers go on a `vX.Y.Z` release, model packages on a separate `model-…` release, so app
  releases don't re-upload weights. Weights are never committed to the repo (`.gitignore`); Git LFS was not used
  because its free quota is far below what public clones of 3.8 GB would need.

## Data folder
`%LOCALAPPDATA%\OpenOne` (Windows), `~/Library/Application Support/OpenOne` (macOS); the portable zip keeps it in
`data\` next to the exe. It holds:
- `models/`, `runtimes/` and `cache/dequant/`;
- `settings.json` and `remote.key`;
- `logs/`: `app.log`, `worker.log`, `runtime.log`, and the opt-in `decisions.jsonl`;
- `feedback.jsonl`.

The uninstaller asks before deleting it.

## Tests
- `tests/test_core.py`: 33 unit tests (the dequant ones need torch).
  - Covered: tampered and unsafe zips, strict JSON, schema errors, 9 kinds of corrupted response that must fail
    validation, provisional fallback settings, gate precedence, and the dequant math.
- `tests/e2e_api.py`: the full app API against real packages:
  - import, start, gate, bucket, raw mode, validation errors, overrides, batch + export, feedback;
  - the FP8 fallback, cached and uncached;
  - the remote backend.
- `tests/tiny_model_smoke.py`: the inference path without private weights (used by CI).
- `tests/smoke_worker.py`: the worker + pipeline on a given runtime, device and package.

## Review
Three read-only review rounds by gpt-6.1-sol (via Codex):
- **Round 1:** 10 findings. 9 were fixed, covering:
  - deletion-path containment;
  - backend start/stop races and settings captured with the backend;
  - fail-closed gate auth, no redirects with the API key;
  - non-finite numbers, Windows filename collisions, verdict validation.
  - Logging invalid *requests* as feedback was declined, and the reviewer accepted that.
- **Round 2:** confirmed those fixes and found 4 follow-ups, all fixed.
- **Round 3:** confirmed those and found 1 last race (replacing a package while it starts), also fixed.

Every fix has a regression test in `tests/test_core.py`.
